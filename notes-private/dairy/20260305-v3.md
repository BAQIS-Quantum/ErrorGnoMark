# 架构重构思路追踪记录  
## —— 从 `core/data` 困惑到 7 层架构清晰化

**日期：** 2026-03-05  
**项目：** EGM  
**阶段：** 架构重构与层级规范化  
**性质：** 架构认知升级 + 结构重建记录

# 一、问题起点：我到底在困惑什么？

在最初的结构中，项目存在如下目录：
core/
├── circuits
├── backends
├── execution
├── experiments
├── analysis
├── data

其中 `data/` 是一个早期设想模块。

它的原始设想是：

> “专门用来处理所有数据相关内容的模块。”

但问题在于：

- 它没有明确边界
- 没有清晰职责定义
- 没有层级归属
- 没有依赖方向约束
- 尚未真正设计
- 只是一个概念性容器

随着项目复杂度上升，我开始产生困惑：

- data 到底应该是什么？
- 它属于哪一层？
- 是否需要单独存在？
- 是否会破坏依赖方向？
- 是否会变成新的“垃圾桶模块”？
- 我是不是在过度设计？

这成为本次重构的核心问题。

---

# 二、关键认知突破：Data 不是一个层

在重构过程中，我逐渐意识到一个重要原则：

> Data 不是一个架构层级，而是一种跨层关注点。

在 Clean Architecture 和工业级软件设计中：

- 数据结构存在
- 但“Data Layer”通常不存在

所谓 “data/” 模块，在很多项目中会变成：

- DTO
- ORM
- 领域模型
- 持久化逻辑
- 运行时状态
- 缓存
- JSON 结构
- 配置
- 实验结果

全部混在一起。

这种结构违反：

- 单一职责原则（SRP）
- 依赖反转原则（DIP）
- 分层隔离原则
- 长期可维护性
- 可扩展性

这类模块在软件工程领域通常被视为：

> 语义塌缩模块（Semantic Collapse Module）

它往往出现在：

- 项目早期
- 架构尚未清晰
- 对分层模型理解尚未成熟的阶段

---

# 三、重新分类：系统中到底有哪些“数据”？

经过拆解，我将系统中的“数据”明确划分为四种类型。

---

## 1️⃣ 领域模型（Domain Model）

例如：

- ExperimentRun
- ErrorBudget
- HardwareSpec
- DeviceTopology

特点：

- 有明确业务语义
- 表达系统概念
- 不关心执行逻辑
- 不关心数据库

✅ 应属于：
egm/domain/

---

## 2️⃣ 结构化数据契约（Schemas / DTO）

例如：

- ExperimentConfig
- ResultSchema
- API Response Model
- JSON 验证结构

特点：

- 纯结构
- 无业务行为
- 用于序列化与验证

✅ 应属于：

egm/schemas/

---

## 3️⃣ 运行态上下文（Runtime State）

例如：

- ExecutionContext
- BackendContext
- ShotConfig

特点：

- 生命周期短
- 强依赖执行引擎
- 属于运行时逻辑

✅ 应属于：

---

## 4️⃣ 持久化与生命周期管理（Persistence）

例如：

- SQLite 存储
- 实验历史查询
- Artifact 保存
- 版本追踪

特点：

- 属于编排层
- 不属于领域建模
- 不属于执行逻辑

✅ 应属于：

egm/suites/

---

# 四、重要结论：删除 data/

最终结论非常清晰：

✅ 不需要单独的 `data/` 模块  
✅ 它不是一个合法架构层  
✅ 它会导致语义混乱  
✅ 它破坏依赖方向清晰性  

因此：

> data/ 被完全拆散，并分配到 domain / schemas / engine / suites 中。

这一步是架构成熟的标志。

---

# 五、关于 datastore 的再思考

在讨论中，我提出：

> 当初其实是想做一个实验数据管理系统。

这触发了新的问题：

是否应该保留一个数据管理子系统？

经过分析得到新的判断：

如果未来需要：

- 数据血缘追踪
- 数据版本控制
- 大规模实验数据库
- 实验复现能力
- 实验 lineage 图
- 查询接口

那应该构建：

egm/datastore/

但前提是：

- 它必须是一个真正的子系统
- 不是模型容器
- 不参与执行逻辑
- 位于 L6 编排层

当前阶段：

✅ 只保留接口定义  
✅ 不实现  
✅ 不让其他层依赖它  
✅ 需求驱动开发  

这避免了“过度架构”。

# 七、为什么我一开始没有想清楚？

这是一个非常重要的反思。

原因包括：

### 1️⃣ 早期关注“功能实现”，而非“结构抽象”

在项目初期，我更关注：

- 怎么跑电路
- 怎么实现 RB
- 怎么调用 backend

而不是：

- 结构是否稳定
- 依赖是否合理
- 层级是否清晰

---

### 2️⃣ 对 Clean Architecture 理解尚未系统化

我当时没有清晰区分：

- 领域模型
- 数据传输对象
- 运行时上下文
- 持久化逻辑

它们都被笼统称为“data”。

---

### 3️⃣ 典型的架构成长路径

软件架构往往经历：

1. 功能驱动阶段
2. 模块分离阶段
3. 层级重构阶段
4. 架构抽象阶段
5. 可演化设计阶段

今天的重构，实际上是从阶段 2 进入阶段 3。

---

# 八、在软件工程领域，这属于什么问题？

这属于：

- 分层架构设计问题
- 模块语义清晰性问题
- 依赖方向管理问题
- 架构成熟度问题

更具体地说：

> 这是一次从“结构组织”向“架构设计”的转变。

---

# 九、今天的核心收获

✅ Data 不是层  
✅ 模块必须有清晰语义  
✅ 依赖方向必须严格  
✅ 不要提前实现未来系统  
✅ 需求驱动扩展  
✅ 抽象优于堆积
