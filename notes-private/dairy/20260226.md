# EGM 实验协作与主线集成治理策略

## 1. 背景与问题定义

当前 EGM 项目同时存在两条并行推进路径：

### 1.1 主线工程（产品流）

- 目标：完成工程治理升级
- 冻结架构边界
- 建立稳定分支模型
- 建立 CI 与发布节奏
- 保证长期可维护性
- 为后续工程师入职做好结构准备

### 1.2 实验协作（实验流）

- 对接外部合作方
- 快速进行算法或系统验证
- 允许一定程度的临时性实现
- 实验成果最终需要体现在 EGM 主结构中

核心问题不是 Git 如何操作，而是：

> 如何在允许实验高速推进的同时，避免主线架构再次失控？

---

# 2. 治理目标

本策略旨在确保：

1. 主线结构长期稳定
2. 实验不污染架构
3. 实验成果可以有序回流
4. 架构演进是受控的，而不是被实验节奏驱动的
5. 工程复杂度不随协作增长而失控

---

# 3. 基本原则

## 3.1 单一真实结构原则

EGM 主仓库是唯一真实结构来源。

- 架构边界只在主仓库定义
- 模块层级只在主仓库确立
- 依赖方向只在主仓库允许修改
- execution 作为子系统的定义不可被实验改变

实验代码不能定义长期结构。

---

## 3.2 实验隔离原则

实验必须与主线隔离：

- 不允许直接在 develop 上进行实验开发
- 不允许 exp 分支直接 merge 到 develop
- 不允许合作方直接改动主线结构
- 不允许实验逻辑跨越既定边界

实验是“能力探索”，不是“结构制定”。

---

## 3.3 抽象优先原则

实验代码回流时必须经过抽象清洗：

> 回流的是抽象能力，而不是实验细节。

示例：

✅ 可以回流：
- 新的抽象接口
- 可复用的执行策略
- 可扩展的 backend 适配层

❌ 不可以回流：
- 针对某个合作方的特判逻辑
- 快速绕过边界的 hack
- 修改依赖方向的临时修补

---

## 3.4 结构变更受控原则

凡是涉及：

- 新目录创建
- 目录移动
- execution 结构调整
- 依赖方向变化

必须单独 PR，不能与功能合并混在一起。

---

# 4. Git 分支治理模型

## 4.1 仓库结构（单仓库策略）

```
main
develop
feature/*
exp/*
```

### 含义

- main：稳定发布版本
- develop：唯一集成主线
- feature/*：功能或架构变更
- exp/*：实验协作分支

---

## 4.2 本地工作区结构

推荐双工作目录：

```
egm-main  → checkout develop
egm-exp   → checkout exp/collab-xxx
```

优势：

- 思维隔离
- 降低误提交风险
- 可使用不同虚拟环境
- 主线与实验物理隔离

不推荐单目录频繁切换分支。

---

# 5. 实验回流主线的标准流程

严禁：

```
exp/collab-xxx → develop
```

必须采用：

```
exp/collab-xxx
        ↓
抽象与重构
        ↓
feature/integrate-xxx
        ↓
PR → develop
```

---

## 5.1 回流前必须回答的三个问题

### 1. 这是实验细节，还是抽象能力？

- 如果是细节，不应进入主线。
- 如果是能力，可以考虑抽象后回流。

---

### 2. 是否改变依赖方向？

如果会改变：

- 必须单独 PR
- 必须写清楚变更原因
- 必须确认不会破坏 execution 边界

---

### 3. 是功能扩展，还是结构调整？

- 功能扩展：正常 feature
- 结构调整：慎重处理，单独审查

---

# 6. 架构稳定期的控制策略

当前阶段目标是：

- 冻结 execution 边界
- 冻结 domain 层结构
- 不进行 server 拆分
- 不做插件系统
- 不引入分布式执行

因此：

> 实验不能推动架构级别重构。

允许小幅度调整，但必须受控。

---

# 7. 合作方协作模式

推荐两种方式：

## 7.1 Fork 模式（推荐）

合作方 fork 仓库：

```
your-org/egm
        ↑
collaborator fork
```

他们通过 PR 合入 exp/*。

优点：

- 权限清晰
- 主线安全
- 风险隔离

---

## 7.2 exp 分支协作模式

给予合作方：

- exp/* 分支权限
- 不给予 main / develop 权限

---

# 8. 架构变更记录机制

建议新增：

```
ARCH_CHANGELOG.md
```

记录：

- 每次结构调整
- 调整原因
- 影响模块
- 是否改变依赖方向
- 是否影响 execution 子系统

目的：

> 明确架构是在进化，而不是震荡。

---

# 9. 风险分析

## 9.1 最大风险

不是实验存在，而是：

- 实验未经抽象直接进入主线
- 实验节奏驱动架构方向
- 结构变更与功能变更混在一起

---

## 9.2 可接受风险

- 小规模结构优化
- 抽象层补充
- 为长期能力扩展预留接口

前提：不破坏边界。

---

# 10. 角色定位

在该模型下：

- 实验开发者：推进验证
- 合作方：提供需求与场景
- 你：架构守门人

你的职责不是写实验代码，而是：

- 定义接口
- 定义抽象
- 控制复杂度
- 审查依赖方向
- 决定什么可以回流

---

# 11. 一句话战略原则

> 实验驱动能力演进，但不驱动结构演进。

---

# 12. 最终目标状态

当该策略运行稳定后，应达到：

- 所有实验在 exp/*
- 所有结构稳定在 develop
- 所有发布从 main 出
- execution 成为真正子系统
- 合作方无法直接影响架构边界
- 架构演进有记录、有节奏、有控制

---

# 13. 结论

采用：

- 单仓库
- develop 为唯一主线
- exp 隔离实验
- feature 中转回流
- 双本地工作目录
- 架构变更单独 PR
- 架构变更记录机制

可以在保持实验推进效率的同时，确保主线工程长期稳定。

该策略适用于：

- 3–6 人团队
- 存在外部协作
- 正处于架构稳定期
- 目标是工程治理升级而非快速重构
