# QuantumCircuit 中 Qubit 标识映射的工程化设计说明

本文整理并总结了此前关于 circuit 修改问题的完整工程背景、问题定性以及对应的设计决策，目的是以一种对合作者友好的方式，说明该问题为何出现、它在软件工程中属于哪一类问题，以及为何当前方案在工程上是正确、克制且可扩展的。

在当前 `errorgnomark/circuits/circuit.py` 的实现中，QuantumCircuit 内部统一使用 `int` 作为逻辑 qubit 的表示方式，例如 `Gate("cnot", (0, 1))`。这一设计并非权宜之计，而是量子编译系统中一个核心且必要的工程前提：所有 gate 的 decomposition、矩阵构造、逆运算、等价性判断以及哈希行为，都依赖 qubit 索引的稳定性、可排序性与可比较性。从工程角度看，`int` 构成了逻辑 qubit 的 canonical representation，是整个中间表示（IR）能够保持数学封闭性、可组合性与可复用性的基础。

与此同时，在真实的工程环境中，尤其是在电路需要对接量子硬件或执行 backend 时，qubit 往往并不只是一个抽象的编号，而是带有明确物理或系统语义的标识符，例如 `sisq-q2-c`、`ibmq_lima_q3` 或 `trap-A-ion-7`。这些标识对于硬件调度、控制资源绑定以及执行日志是必需的，但它们并不适合直接进入现有的 gate 与 decomposition 逻辑中。由此产生的工程矛盾并不是“Gate 是否应该支持 string 类型的 qubit”，而是一个更根本的问题：如何在不破坏既有量子编译与代数逻辑的前提下，引入外部 qubit 标识能力。

从软件工程的角度看，这一问题可以被明确地归类为编译器与中间表示（IR）系统设计问题，涉及量子编译器工程、IR 抽象与稳定性设计、前端–后端解耦，以及逻辑资源与物理资源映射等多个子领域。本质上，这是一个 IR 边界与职责划分的问题，而不是量子算法或数学建模问题。现有系统中已经隐含了一组必须被严格遵守的工程约束：Gate 层是数学封闭的，其 `qubits` 类型固定为 `Tuple[int, ...]`，所有 decomposition rule、矩阵定义与逆运算均假设 qubit 是整数索引，因此 Gate 层既不应也不允许感知任何外部或物理语义；decomposition 引擎是纯逻辑的，只负责 gate 的展开与 basis 收敛，与硬件或执行环境无关；QuantumCircuit 的正确定位是逻辑量子电路的 IR 容器，而不是物理执行计划或硬件抽象层。

在明确这些不可破坏的边界之后，问题的本质可以被抽象为一个双命名空间（dual namespace）的设计问题：系统一方面需要稳定、可计算的逻辑命名空间（以 `int` 表示的 qubit），另一方面又需要面向 backend 的外部或物理命名空间（以 `str` 表示的标识），并且二者之间必须存在清晰、单向、不会污染 IR 语义的映射关系。由此推导出的设计目标也非常明确：内部所有算法继续只使用整数 qubit；外部标识仅作为附加信息存在；Gate、matrix 与 decomposition 逻辑完全不修改；backend 可以直接读取已有语义，而无需推断或发明新的含义。

基于上述分析，核心设计决策是仅在 `QuantumCircuit` 层引入一个可选、非侵入式的映射结构，例如 `qubit_ids: Dict[int, str]`，用于表达逻辑 qubit 与外部标识之间的对应关系。在这一设计中，逻辑 qubit（`int`）始终是 source of truth，而外部标识只是附加的元数据。通过提供诸如 `set_qubit_ids` 的接口，可以同时支持列表形式的用户友好输入与显式字典形式的编译器级输入；同时，通过一个统一的解析接口（例如 `resolve_qubit`），backend 在读取 qubit 信息时无需额外的分支逻辑：若存在外部标识则返回字符串，否则回退为原始的逻辑索引。

从工程正确性的角度看，该设计完整地保持了 IR 的纯度与稳定性，所有数学与编译逻辑实现零修改，外部标识作为正交关注点存在，不影响电路的等价性、可分解性或可复制性。系统各层的职责边界依然清晰：Gate 负责数学定义，decomposition 负责逻辑展开，QuantumCircuit 负责 IR 容器与元数据管理，而 backend 负责物理资源的绑定与执行调度。这一架构思想在工程实践上也与 Qiskit、Cirq、t|ket> 等工业级量子编译器在逻辑到物理映射上的设计保持一致。

因此，这次修改并不是一次临时性的功能补丁，而是一次符合编译器工程原则的 IR 扩展。它在保持现有系统严格正确性的同时，引入了对真实硬件与 backend 友好的扩展能力，并为未来进一步引入调度机制、噪声模型或物理约束提供了稳定且可维护的架构基础。
