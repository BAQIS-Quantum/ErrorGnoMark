# circuit.py — qubit string 逻辑处理思路

---

## 工程领域归属

✅ 工程软件开发领域  
→ 编译器与中间表示（IR, Intermediate Representation）系统设计

在工程视角下，它同时涉及以下子领域：

- 量子编译器工程（Quantum Compiler Engineering）
- 中间表示（IR）抽象与稳定性设计
- 前端–后端解耦（Frontend / Backend Decoupling）
- 逻辑资源与物理资源映射（Logical → Physical Resource Mapping）

本质上，这是一个 **IR 边界与职责划分问题**。

---

## 现实系统中的必然性

这在现实系统里非常常见，而且是不可避免的，原因包括：

### 1. 同一逻辑 qubit 在不同实验模式下

- 使用不同测控链路  
- 一条测量通道  
  → 可能被多个逻辑 qubit 复用 / time‑multiplex  
- 不同芯片 / 不同 rack  
  → qubit index 只是“局部视图”

---

## 为什么不应该把这个逻辑丢给 egm‑to‑sisq converter？

### ✅ 原因 1：converter 层不应该“发明语义”

converter 的职责应该是：

- 读取 egm circuit 中已经存在的语义
- 转换为 SISQ 可接受的格式

而不是：

- ❌ 推测 qubit index 背后代表什么
- ❌ 根据硬编码规则生成通道编号
- ❌ 维护第二套 qubit mapping

否则：

- converter 会变成半个 compiler
- bug 边界极难控制
- 两边版本演进会互相拖死

---

### ✅ 原因 2：你现在的 circuit 层已经是“唯一的稳定抽象层”

从你这份代码可以非常清楚地看到：

- 所有 gate 都绑定在 `qubits: Tuple[int, ...]`
- 所有 decomposition / inverse / matrix  
  完全依赖 qubit identity 的一致性

circuit 是：

- 可复制
- 可组合
- 可逆
- 可多次分解

👉 这正是最适合承载“附加 qubit 语义”的地方

---

### ✅ 原因 3：egm 自己未来一定也会用到这些信息

哪怕不考虑 SISQ，对 egm 自身来说：

后续做：

- scheduling
- qubit remapping
- multi‑device execution
- noise model / calibration

都迟早会需要区分：

- “这是哪个逻辑 qubit？”
- “它实际落在什么物理 / 控制资源上？”

---

## 最终解决方案

保持 Gate / decomposition / matrix **100% 不变**，  
在 QuantumCircuit 上增加“可选的 qubit 资源绑定信息”。

---

## QuantumCircuit 层的扩展设计

在 QuantumCircuit 层，引入两类 **可选信息**：

---

### 1️⃣ Qubit External ID（对方说的“那串字符串”）

**语义：**

> “这个逻辑 qubit，在提交到硬件 / SISQ 时，对应的外部编号”

**形式（概念）：**

- logical qubit 0 → `"Q3"`
- logical qubit 1 → `"Q4"`

它可能代表：

- 物理 qubit id
- 设备路径
- 控制资源名
- SISQ 接口要求的 qubit 标识

egm 不解析、不解释，只保存。

---

### 2️⃣ （可选）Channel / Control Resource Binding

这是下一步，但你现在已经意识到方向是对的。

- logical qubit 0 →
  - drive   : `"Q3.d"`
  - measure : `"Q3.m"`

同样：

- egm 不理解含义
- 只是一个稳定的 key‑value 容器
