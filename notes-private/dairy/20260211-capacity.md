# EGM 分层重构方案（升级版）：Capability 与 Compiler 融合后的最终架构设计

**日期：** 2026-02-11  
**项目：** ErrorGnoMark (EGM)  
**主题：** Capability 层定位 + 编译优化器（Compiler）接入后的完整架构方案

---

# 一、问题背景

在 EGM 架构演进过程中出现两个关键问题：

1. Capability（能力）测试必须经过量子编译 / 拓扑映射 / 优化  
   → 是否仍属于 Physical 层？

2. 如果未来接入量子编译优化器（Compiler / Transpiler / Optimizer），  
   → 是否会破坏当前分层结构？

经过系统性分析，我们发现：

- Capability 不是 native gate 噪声层
- 也不是 logical 编码层
- Compiler 也不属于 evaluation 层

这说明 EGM 需要：

✅ 四层 evaluation 结构  
✅ 横向 execution & compilation 基础设施层  

---

# 二、Capability 的最终定位

## 2.1 Physical Benchmark 本质

```
原生门
  ↓
执行
  ↓
误差估计
```

关注：

- 门保真度
- T1 / T2
- 读出误差
- 串扰
- 噪声模型

定义：

> 纯硬件本征性能表征

---

## 2.2 Capability Benchmark 本质

```
抽象结构电路
  ↓
编译 / 拓扑映射
  ↓
原生门
  ↓
执行
  ↓
结构资源分析
```

关注：

- 纠缠容量
- 非定域深度
- Magic 资源生成能力
- Contextuality
- 多体关联结构

定义：

> 系统级量子资源生成能力评估

关键区别：

Capability 是系统整体结构能力，而非单门误差。

---

# 三、Compiler 的本质定位

Compiler 的作用：

```
抽象电路
   ↓
编译 / 优化 / 拓扑映射
   ↓
硬件可执行电路
```

它：

- 不属于 Physical
- 不属于 Capability
- 不属于 Logical
- 不属于 Algorithmic

它属于：

> 横向执行基础设施（Execution Infrastructure）

它是跨层转换器，而非评估层。

---

# 四、最终架构：四层 + 横向基础设施

---

## ✅ 垂直 Evaluation Layers

### Layer 1 — Physical Performance Layer

- 原生门保真度
- T1 / T2
- Crosstalk
- 噪声模型

---

### Layer 2 — Quantum Capability Layer

- Entanglement capacity
- Nonlocality depth
- Magic generation
- Contextuality
- Multi-qubit correlation strength

特点：

- 需要编译
- 不涉及编码
- 不依赖应用

---

### Layer 3 — Logical Layer

- Logical fidelity
- Threshold estimation
- Distance scaling
- Decoder performance

---

### Layer 4 — Algorithmic Performance Layer

- Algebraic algorithms
- Simulation tasks
- Variational / Hybrid methods
- Convergence analysis
- Resource cost

---

## ✅ 横向 Execution & Compilation Infrastructure

包含：

- Compiler
- Optimization passes
- Backend interface
- Job scheduling
- Circuit IR 管理

位置：

横跨四层，服务所有 evaluation 层。

# 七、反思：这次架构升级意味着什么？

你解决的不是：

“Capability 放哪？”

而是：

> 抽象边界冲突问题（Abstraction Boundary Conflict）

你避免了：

- 将 Capability 错放入 Physical
- 将 Compiler 混入 Evaluation 层
- 层级污染（Layer Contamination）
- 未来扩展崩塌

最终形成：

垂直评估结构 + 横向基础设施结构

这是成熟系统工程的典型形态。

EGM 应采用：

✅ 四层 Evaluation 架构

✅ Capability 独立于 Physical 与 Logical

```
Physical Noise

      ↓
Logical Error Suppression
      ↓
Algorithmic Performance
```

Compiler 横跨其间，但不属于任何一层。

# 1. 起点：从海报思想到架构演化

最初海报的核心关注点是：

- 使用 Svetlichny inequality
- 检测 genuine multipartite nonlocality
- 强调 device-independent structural verification
- 将 nonlocality 视为比普通 entanglement 更强的资源
- 用于 near-term quantum processor 的能力评估

海报背后的逻辑结构为：

Quantum Foundations  
→ Nonlocal Structure  
→ Resource Strength  
→ Computational Potential  

它关注的不是：

- gate fidelity
- 电路精度
- 噪声参数

而是：

> 量子设备是否真正生成了深层非经典结构。

---

# 2. 海报思想如何嵌入 EGM

EGM 当前是一个 full-stack 架构：

core → domain → suites → reporting → server → sdk

在 core 层中已有实验分类：

core/experiments/
- benchmarking/
- characterization/

问题在于：

- 海报思想不属于 performance benchmarking
- 也不属于 noise characterization
- 它属于结构能力层

因此需要新增一个抽象层级。

---

# 3. Entanglement Fidelity 的定位澄清

当前结构：

core/experiments/characterization/entanglement/
- bell_fidelity.py
- ghz_fidelity.py
- graph_state_fidelity.py

Entanglement fidelity 的本质是：

- State validation
- Target state verification
- 实验刻画

它回答：

> 是否成功制备了预期态？

它不回答：

> 设备是否具有生成强量子结构的能力？

因此最终决定：

✅ Entanglement fidelity 保持在 characterization  
❌ 不移动到 capability  

这是“状态验证”与“结构能力”的清晰边界。

---

# 4. Capability 概念的确定

在讨论中出现的候选词包括：

- resource
- nonclassical
- structure
- certification
- capability

最终选择：

# ✅ Capability

选择原因：

1. 不过度绑定 resource theory
2. 不偏基础物理语义
3. 不与 benchmarking 冲突
4. 同时覆盖结构层与资源层意义
5. 强调能力而非单次实验结果

Capability 的正式定义：

Quantum Capability =  
The operational ability of a quantum processor to generate, preserve, and manipulate key non-classical structural features underpinning quantum computational power.

中文表述：

> 量子设备生成和维持关键量子结构资源的能力。

---

# 5. EGM 四层逻辑体系

通过本次梳理，EGM 形成四层逻辑结构：

Layer 1 — Benchmarking  
→ Gate / circuit performance  

Layer 2 — Characterization  
→ Physical noise mechanisms  

Layer 3 — Capability  
→ Structural quantum ability  

Layer 4 — Algorithmic  
→ Application-level behavior  

逻辑链条：

Physics errors  
→ Operational performance  
→ Structural capability  
→ Algorithmic utility  

这构成完整的 Physics → Capability → Application 评估路径。

---

# 6. Capability 与其他层的边界

Benchmarking  
- 回答：算得准不准？  
- 示例：RB, XEB  

Characterization  
- 回答：噪声来自哪里？  
- 示例：T1, T2  

Capability  
- 回答：是否具备量子结构能力？  
- 示例：Bell, Svetlichny, contextuality  

Domain Analysis  
- 回答：噪声如何影响能力？  
- 示例：capability decay  

核心区分：

Characterization = 物理层  
Capability = 结构层  
Benchmarking = 操作层
