# 关于“先研究框架，后封装 API”的策略说明

## 背景

当前 EGM 处于研究型框架阶段：

- 分类体系仍在演进
- 实验结构可能频繁调整
- 抽象模型尚未完全稳定
- 用户形态尚未完全明确

因此，暂不设计产品级稳定 API，而优先保证研究结构的表达能力与演进自由度。

---

# 战略决策

## ✅ 当前阶段策略

先构建研究型框架（Research-Oriented Architecture），  
未来在结构基本稳定后，再封装稳定的 Public API 层。

---

# 为什么现在不做 API？

在研究阶段过早冻结 API 会带来：

- 抽象被错误锁定
- 分类无法自然演进
- 概念重构成本变高
- API 成为架构负担

研究阶段的核心目标是：

> 建立正确的知识结构，而不是优化用户调用路径。

---

# 风险识别：隐形 API 问题

即使未正式设计 API，也可能无意中形成“隐形 API”。

如果出现以下行为：

- README 中展示深层 import 示例
- 文档公开内部路径
- 合作方依赖深层目录结构
- 论文或示例代码使用内部路径

那么内部研究结构实际上已经变成了外部依赖接口。

这会在未来结构调整时带来极高成本。

---

# 当前约束原则

在研究阶段必须遵守以下原则：

1. 明确声明：
   - `egm.core.*` 属于内部研究结构
   - 不保证路径稳定
   - 不承诺向后兼容

2. 避免在官方文档中展示深层 import 路径

3. 不承诺接口稳定性

4. 保持模块边界清晰，避免跨层耦合

---

# 未来演进路径

## 阶段 1：研究阶段（当前）

- 深层目录结构
- 快速概念迭代
- 不保证路径稳定
- 以知识表达为优先

---

## 阶段 2：准产品阶段

- 分类体系趋于稳定
- 抽象模型成熟
- 合作方开始长期依赖
- 版本开始具备语义意义

---

## 阶段 3：稳定 API 阶段

- 引入 public 导出层
- 建立 egm.api / egm.benchmarks 等稳定入口
- 内部结构允许继续演进
- 外部接口保持稳定
- 引入 deprecation 策略

---

# 关键架构原则

> Research 结构可以深。  
> Public API 必须浅。  
> 两者之间应存在缓冲层。

---

# 判断未来是否需要 API 层的标准

当满足以下条件时，应考虑引入稳定 API：

- 目录结构不再频繁调整
- 抽象接口稳定超过 1–2 个版本周期
- 合作方开始长期依赖
- 重构成本明显上升

---

# 结论

当前阶段：

✅ 专注研究型架构  
✅ 保持结构清晰与语义稳定  
✅ 控制隐形 API 风险  

未来阶段：

✅ 在结构成熟后再封装稳定 API  
✅ 保持“内部不稳定，外部稳定”的设计哲学  

---

# 核心一句话

> API 不是现在要优化的对象。  
> 抽象质量才是。
