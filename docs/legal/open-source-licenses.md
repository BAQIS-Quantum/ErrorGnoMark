# 开源许可证说明（EGM 为何采用 Apache-2.0）

> 读者：课题组成员、合作方、企业评估人员  
> 目的：用通俗语言说明常见许可证的区别，以及 ErrorGnoMark（EGM）选择 **Apache License 2.0** 的原因。  
> **本文不是法律意见**；单位对外发布前，如有知识产权办公室，可请其复核。

**当前项目许可证（自 v3.0.3 起）：** [Apache License 2.0](../../LICENSE)（SPDX：`Apache-2.0`）  
**历史与变更记录：** [LICENSE-AUDIT.md](../../LICENSE-AUDIT.md)

---

## 一、先记住三句话

1. **许可证**回答的是：别人能不能用、改、分发你的代码，以及要遵守什么条件。  
2. **MIT / BSD** 很短、很宽松，但几乎**不谈专利**。  
3. **Apache-2.0** 同样宽松，但多了**专利授权**和**变更说明（NOTICE）**，企业法务更常认可。  
4. **GPL** 更「传染」：把 GPL 代码合进产品后，往往要求**整个相关产品也要开源**，一般不适合「希望被商业产品集成」的平台型工具。

**EGM 的选择：** 我们要方便学术使用，也要方便实验室和企业**放心集成**，所以用 **Apache-2.0**，并在 `LICENSE`、README、PyPI 上保持一致。

---

## 二、四个词先搞懂（不用背法条）

| 概念 | 通俗理解 |
|------|----------|
| **版权（Copyright）** | 谁写的代码，谁有著作权；许可证是在著作权之下，授予他人使用权。 |
| **专利（Patent）** | 保护「想法/方法」的权利，和「复制粘贴代码」不是一回事；企业特别关心「用你们的算法会不会被告专利」。 |
| **Copyleft（著佐权）** | 「你改了我的代码再分发，也要按同样规则开源」；**GPL** 是典型。 |
| **NOTICE** | 分发软件时，要保留版权/专利/变更说明等声明；**Apache-2.0** 对此有明确要求。 |

## 三、常见许可证一张表（EGM 相关）

| 许可证 | 一句话 | 别人能否商用 | 能否改闭源再卖 | 专利条款 | 传染性 | 典型用户 |
|--------|--------|--------------|----------------|----------|--------|----------|
| **MIT** | 很短，「随便用，保留版权声明」 | ✅ | ✅ | 几乎无 | 无 | 小工具、库、前端组件 |
| **BSD-3-Clause** | 和 MIT 很像，多一条「不能用作者名义背书」 | ✅ | ✅ | 几乎无 | 无 | 学术库、系统组件 |
| **Apache-2.0** | 宽松 + **明确专利授权** + NOTICE 要求 | ✅ | ✅ | **有** | 无 | Android、很多 Apache 项目、企业友好库 |
| **GPL-3.0** | 可用，但衍生分发常要**整体开源** | ✅* | ⚠️ 受限 | 有 | **强** | Linux 内核、坚持全开源的项目 |

\* GPL 也允许收费，但通常要求提供源代码，商业「闭源集成」困难。

**和 EGM 的关系：**

- 我们**不是**要把所有衍生作品都强制开源（所以**不选 GPL** 作为主许可证）。  
- 我们希望企业集成时**专利风险更清晰**（所以**倾向 Apache-2.0 而非仅 MIT**）。  
- 我们仍保持**宽松**：别人可以商用、修改、分发，只要遵守 Apache-2.0 条件。

## 四、稍微展开：MIT、Apache-2.0、GPL

### MIT — 「极简宽松」

- **优点：** 短、好懂、争议少、和几乎所有其他许可证兼容。  
- **缺点：** 几乎**不处理专利**；大公司有时会问：「如果作者后来主张专利怎么办？」  
- **适合：** 个人小项目、示例代码、不强调企业合规文档的库。

### Apache-2.0 — 「宽松 + 专利写清楚」

- **优点：**  
  - 和 MIT 一样允许商用、修改、私有使用、分发。  
  - **贡献者授予专利许可**，降低企业用户的专利顾虑。  
  - 业界成熟，Android、Kubernetes 等大量项目使用，法务模板多。  
- **代价：**  
  - 文本比 MIT 长。  
  - 分发时若修改了文件，需在修改处**注明**；有 NOTICE 文件时要一并保留。  
- **适合：** 希望被**企业、云平台、实验室系统**集成的工具与平台 — **EGM 属于这类**。

### GPL-3.0 — 「开源传染」

- **优点：** 保证衍生作品也保持开源，符合「自由软件」理念。  
- **缺点：** 若把 GPL 代码**链接/集成**进闭源产品，往往触发开源义务 — 企业集成成本高。  
- **适合：** 明确希望「任何基于本项目的分发都要开源」的项目。  
- **EGM 不采用为主许可证的原因：** 目标是 QCVV 平台与数据层被**广泛采用**（含商业栈），而非强制下游全部 GPL 开源。

## 五、为什么 EGM 用 Apache-2.0（而不是 MIT 或 GPL）

| 我们的目标 | Apache-2.0 是否匹配 |
|------------|---------------------|
| 学术论文、开源社区可自由使用 | ✅ |
| 实验室 / 企业可把 EGM 当组件集成 | ✅（无 GPL 式传染） |
| 对外表述一致、可信（LICENSE = README = PyPI） | ✅ 已统一 |
| 合作方（单位、基金）常见合规审查 | ✅ 比纯 MIT 更易过「专利」问答 |
| 不强制所有改动的衍生项目必须开源 | ✅（区别于 GPL） |

**历史说明（避免困惑）：**

- 仓库根目录 `LICENSE` 很早就接近 **MIT** 文本。  
- 早年 README / PyPI 曾误标 **Apache**，造成「文不对题」（见 [LICENSE-AUDIT.md](../../LICENSE-AUDIT.md)）。  
- **v3.0.1** 曾统一为 **MIT**。  
- **v3.0.3 起** 经维护方决定，正式采用 **Apache-2.0**，以更好匹配**学术 + 企业采用**的长期定位。

## 六、对不同角色意味着什么

### 使用者（pip install / clone 使用）

- 可以免费用于研究、教学、商业项目。  
- 分发 EGM 或包含 EGM 的产品时，需保留 **LICENSE** 全文及要求的 **NOTICE**（若有）。  
- 不必把你们自己的应用强制开源（在非 GPL 组合的前提下）。

### 贡献者（提 PR）

- 贡献代码即表示在 **Apache-2.0** 下授权项目使用（见 [CONTRIBUTING.md](../../CONTRIBUTING.md)）。  
- 与单位知识产权规定冲突时，应先走单位内部流程。

### 维护者（我们）

- 所有对外入口保持一致：`LICENSE`、`README`、`pyproject.toml`、GitHub License 字段、PyPI。  
- 大版本变更许可证时，更新 [LICENSE-AUDIT.md](../../LICENSE-AUDIT.md) 和 CHANGELOG。

## 七、和「依赖库许可证」的关系

EGM 依赖 NumPy、SciPy 等第三方包；它们各自带 **MIT / BSD / Apache** 等许可证。

- **选 Apache-2.0 作为主许可证**，不表示「整个环境只有 Apache」。  
- 企业若做合规扫描，通常会单独列出**依赖清单（SBOM）**；这是正常现象。  
- Apache-2.0 与常见 MIT/BSD/Apache 依赖**兼容性好**；若引入 **GPL** 依赖，需单独评估（EGM 主链路应避免强 GPL 依赖混入而不说明）。

## 八、常见问题（FAQ）

**Q：Apache-2.0 和 MIT 哪个「更开放」？**  
A：对「能否商用、改、闭源分发」而言，两者都很开放；Apache 多写了**专利**和 **NOTICE**，不是更「封闭」。

**Q：我们能不能改回 MIT？**  
A：可以，但需维护者决策、更新 `LICENSE` 与所有元数据，并在 LICENSE-AUDIT 中记录；已发布版本的历史许可证不会自动改变。

**Q：用户要不要付费？**  
A：许可证不要求付费；你们可以对**服务、支持、托管**收费，与许可证无关。

**Q：Apache 基金会和 Apache-2.0 是一回事吗？**  
A：不是。Apache-2.0 是 OSI 认可的开源许可证；**不等于** Apache 软件基金会背书本项目。

**Q：Gitee / GitHub 两个仓许可证要一致吗？**  
A：若分发的是**同一套源代码**，应一致；镜像仓 LICENSE 文件应与 canonical 仓库相同。
