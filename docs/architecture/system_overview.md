# EGM 系统总体说明（System Overview）

作者：项目负责人  
状态：架构基础文件（Architecture Foundational Document）  
适用范围：所有参与 EGM 开发与协作的成员  

---

## 一、本文档目的

本文档用于明确 EGM 系统的整体定位、结构角色与能力边界。

其目标是：

- 明确 EGM 在整体软件栈中的位置；
- 统一对系统主轴与发展方向的理解；
- 确立系统边界，避免功能性漂移；
- 为后续架构设计与协作提供稳定基础。

所有参与 EGM 核心开发的成员，在修改核心模块前，应充分理解本文件所定义的系统定位与原则。

---

## 二、系统定位

EGM（Evolving Hardware World Model）的核心目标是：

> 构建一个可版本化（Versioned）、可回溯（Traceable）、具备显式时间结构的硬件语义世界模型。

EGM 是一个“语义层”，而非一个控制系统或算法系统。

其关注的问题是：

- 在任意时刻，硬件“世界状态”是什么；
- 状态如何通过事件演化；
- 任意历史决策所依赖的硬件状态是什么；
- 状态演化如何被形式化表达。

EGM 的核心价值在于：

- 显式时间建模；
- 状态不可变性；
- 事件驱动演化；
- 语义结构化表达。

---

## 三、在整体软件栈中的结构角色

可将整体系统抽象为三层结构：

执行层（Execution Layer）  
↓  
EGM 语义层（Semantic Layer）  
↓  
应用层（Application Layer）

### 3.1 执行层

执行层负责：

- 实验调度；
- 数据采集；
- 参数拟合；
- 闭环控制；
- 硬件运行稳定性维护。

EGM 不参与控制逻辑，也不参与调度策略。

执行层向 EGM 提供“事实输入”，而非策略输入。

---

### 3.2 应用层

应用层包括：

- 编译系统；
- 自动化校准策略；
- 调度优化模块；
- AI/研究型模块。

应用层只能通过 Snapshot 读取硬件状态。

应用层：

- 不可直接修改 HardwareState；
- 不可创建 Version；
- 不可绕过 Event 机制。

---

### 3.3 EGM 语义层

EGM 提供：

- 结构化 HardwareState；
- Event 驱动的状态演化机制；
- Version 图（DAG）显式时间结构；
- Snapshot 只读视图。

EGM 的职责是：

> 描述“世界是什么”，而不是决定“世界该如何被使用”。

---

## 四、系统的核心抽象对象

EGM 当前的核心抽象包括：

- HardwareState：结构化硬件状态语义表示；
- Event：对“世界变化”的强类型声明；
- Version：状态演化节点；
- Version Graph：时间结构 DAG；
- Snapshot：绑定特定 Version 的不可变只读视图。

这些抽象构成 EGM 的语义基础。

---

## 五、系统边界声明（Non-Goals）

为避免架构漂移，明确以下非目标：

EGM 不承担：

- 编译算法实现；
- 校准调度策略；
- AI 模型训练；
- 实验控制逻辑；
- 数值优化算法；
- 任务调度与云执行管理。

如未来出现相关需求，应通过扩展层或上层模块实现，而非修改核心语义抽象。

---

## 六、时间结构与语义一致性

EGM 采用 Version Graph 表达时间结构。

设计目的：

- 避免覆盖式状态更新；
- 保证历史可回溯；
- 支持历史决策解释；
- 提供长期演化分析基础。

所有状态变更必须通过 Event 驱动。

严禁绕过 Event 直接修改 HardwareState。

---

## 七、主轴声明

EGM 的主轴是：

> 确定性历史世界模型（Deterministic Historical World Model）。

未来若引入预测或概率模型，应作为独立扩展层存在，不得污染确定性核心。

---

## 八、演化原则

EGM 的演化应遵循：

1. 核心抽象优先稳定；
2. 扩展能力不影响核心语义；
3. 单一应用需求不得反向塑造核心结构；
4. 所有架构修改应经过明确评审。

---

## 九、结语

EGM 的本质，不是功能集合，而是结构承诺。

本系统的长期价值取决于：

- 语义清晰度；
- 时间一致性；
- 抽象稳定性；
- 模块边界纪律。

本文件作为 EGM 架构基础文件，具有长期约束意义。
